# 联网检索（WebSearch / WebFetch）

`WebSearch` 与 `WebFetch` 是 Proma Cloud 的一等工具：一次工具调用就返回结果，不需要写 HTTP 代码、不需要自己取凭据。每次**成功**请求扣 0.0059 积分；空结果、失败、超时都不扣费。

- `WebSearch`：一次聚焦查询返回结构化结果（标题、URL、snippet、summary、发布时间、站点、权威度、相关性分数）。
- `WebFetch`：把一个已知 URL 的正文转成 Markdown（单页 4 万字上限）。

## 先选对工具

| 场景 | 选择 |
| --- | --- |
| 时效性事实：新闻、发布、版本、价格、配额、股价、比赛比分 | `WebSearch` |
| 跨站发现、多来源比对、批量核实 | `WebSearch` |
| 自动任务、委派子会话、后台无人值守（没有可交互浏览器） | `WebSearch` |
| 需要结构化证据（URL + 时间 + 权威度）便于引用 | `WebSearch` |
| 明确给出 URL，或用户点名某篇文章/文档/价格页 | `WebFetch` |
| 搜索结果指向长文档，答案在正文细节里 | `WebSearch` → `WebFetch` 取 1–3 篇 |
| 需要登录、点击、填写、翻页、下载 | 浏览器（`Browser*`） |
| 内容要 JS 渲染后才出现，或需要视觉核验/截图 | 浏览器（`Browser*`） |
| 用户要亲眼看这个页面，或需要用户本人操作 | 浏览器（`Browser*`） |

几条硬规则：

- 稳定知识（数学、语言、代码概念、已给出的对话内容）直接回答，不搜索；搜索不是"更保险"，是花用户的钱。
- 已有 `WebFetch` 能覆盖的单一 URL，不要先用 `WebSearch` 绕一圈。
- 站点需要登录态或交互才能出结果时，不要用 `WebSearch`/`WebFetch` 反复试探，直接转浏览器。
- 同一个查询不要既搜一遍又在浏览器里搜一遍，除非正是在做下一节的互验。

## 并发：一次发出，成组返回

`WebSearch` 与 `WebFetch` 都是无状态只读工具，**同一条消息里发出的多个调用会并行执行**。这是它们相对浏览器的核心优势：广度、速度、可并发。

- 需要多个角度、多个语言、多个站点时，一次发 2–4 个查询，而不是串行一个个来。例如同时发"官方发布说明 site:docs.x.com"和"X 价格 lang:en after:2026"。
- 已知多个 URL 要读正文时，一次并行发 2–3 个 `WebFetch`，不要一个一个等。
- 并发度要克制：用户级限流约为搜索 2 请求/秒、抓取 1 请求/秒（每个进程），一次超过 4 个并发查询容易触发 `429`。宁可两轮各 3 个，不要一轮 10 个。
- 只有存在数据依赖时才串行：先用 `WebSearch` 拿到 URL，再并行 `WebFetch` 取其中几篇。
- 不要并发同一个查询，也不要为了"更快"把同一个问题拆成近义查询并发跑——那是双倍成本、零信息增量。

## 失败、数据不足或结果可疑时：用浏览器补齐

搜索与抓取是**广度工具**，浏览器是**深度与真实性工具**。下面三类信号出现时，不要继续在搜索里打转，转到受管浏览器补齐：

**一、工具失败**

- `402`（积分不足）：停止检索，如实告知；如果用户仍需要这份信息，说明可以用浏览器继续但需要用户确认继续消耗时间。
- `429` / `502` / `503` / 超时：最多按提示重试一次，仍失败就转浏览器。
- `403` / `404`（抓取被拒或无正文）：换 1–2 个来源后仍拿不到，转浏览器打开同一页面（浏览器能处理渲染与部分访问策略）。
- `401`：提示用户检查登录；需要立刻完成时，只能用浏览器（若用户本机登录态有效）。

**二、数据欠缺**

- 结果少于 3 条、或大部分与查询无关；
- 只有 `snippet` 没有 `summary`，也没有 `date`；
- `authority < 3` 或 `rerank_score < 1.5` 占据多数；
- 答案需要站内数据、登录后内容、完整评论链、实时列表或分页数据；
- 关键数字/条款只出现在二手转述里，找不到原始页面。

做法：先用浏览器打开最可能的原始站点（官方文档、定价页、公告页），用 `BrowserObserve`/`BrowserExtract` 取正文；必要时登录后站内搜索。

**三、结果可疑**

- 与用户提供的截图、文档或已知事实冲突；
- 两条 `summary` 说法不一致，或数字对不上；
- 发布时间过旧，但问题问的是"现在"；
- 站点是聚合站、翻译站、AI 生成内容站，或明显 SEO 农场；
- 页面打不开，或被要求验证、登录、同意 Cookie 才能看到内容。

做法：`WebSearch` 找到官方来源 → 浏览器打开原文核对 → 以页面正文为准；仍无法确认就明确告诉用户"未核实"，不要用摘要包装成结论。

**边界**：浏览器补齐不是"再搜一遍"。用浏览器是为了拿到搜索拿不到的东西——登录态、动态渲染、交互后的结果、视觉证据、站内历史；如果只是同一批公开页面，重复劳动没有价值。

## 什么时候两者并用、互相验证

搜索结果只是候选证据，页面正文才是原始证据。下列情况必须"先搜、再打开原文核对"：

- **高风险或易变事实**：价格、配额、额度、版本号、接口字段、政策条款、合规要求、安全公告。答错代价高，且站点经常改。
- **来源之间冲突**：两条 `summary` 说法不一致，或搜索结果与用户提供的截图/文档矛盾。
- **疑似低质来源**：`authority < 3`、`rerank_score < 1.5`、聚合站/内容农场/翻译站的二手转述。
- **页面需要证明"现在仍然是这样"**：文档已迁移、产品页改版、公告被更新时，只看摘要会拿到过期信息。

做法：`WebSearch` 定位候选 → 选 1–2 个高权威来源 `WebFetch`（或转浏览器）→ 以页面正文为准 → 在回复里写清哪个结论来自哪个 URL 和日期。互验只看关键来源，不要把每个结果都打开，那是双重成本。

证据等级：页面正文 > 搜索 `summary` > `snippet`。冲突时按等级取舍并说明分歧；无法确认时明确说"未核实"，不要用搜索摘要包装成确定结论。

## 检索策略

1. 一次用完整语义的聚焦查询，不要把长问题拆成十个小查询。
2. 需要收窄时用运算符：`site:`、`-site:`、`-词`、`"精确短语"`、`lang:`、`after:`、`before:`。
3. `count` 默认 10，价格与条数无关；`need_content` 一般保持 `false`，先读 `snippet`/`summary` 判断相关，再用 `WebFetch` 取正文。
4. 结果取舍：`rerank_score ≥ 1.5` 才算相关，`authority ≥ 3` 才算权威；两者都低的不要用来支撑结论。
5. 传 `ori_question` 写用户的原始问题，能提升查询理解（长问题、含指代的问题尤其有用）。
6. 空结果不算失败：放宽查询、去掉过严运算符、换语言或换关键词，最多再试一次。

## 抓取策略

- 只抓真正要引用的 1–3 篇；`WebFetch` 一次一个 URL，不要对结果列表逐个抓取。
- 内容被截断（返回 `truncated: true`）时，定位到需要的章节即可；不要为了"读全"反复抓同一页。
- 付费墙、需登录、需点击展开的内容直接放弃并换公开来源；不要尝试绕过站点限制。
- 抓取失败按状态码处理，不要对同一个 URL 重试两次以上。

## 错误处理

| 状态 | 含义与动作 |
| --- | --- |
| `400` | 参数不合法（query 为空/超 128 字符、count 越界、URL 非法）。修正后重试一次。 |
| `401` | Proma 登录态可能失效。提示用户检查登录，或改用受管浏览器。 |
| `402` | 用户积分不足。停止检索并如实告知，不重试。 |
| `403` | 目标站点拒绝抓取。换 1–2 个来源后仍失败，转浏览器打开同一页面。 |
| `404` | 该 URL 没有可提取正文；对搜索则可能表示服务端还没有该路由。换来源或转浏览器，不重试同一 URL。 |
| `429` | 触发限流。等待 `Retry-After`（通常 1–2 秒）后最多重试一次。 |
| `502` / `503` | Proma 上游暂时异常。最多重试一次；仍失败就用受管浏览器补齐，或告知用户。 |

## 成本意识

- 自动化任务里尤其克制：同一轮不要重复同一查询，也不要用搜索"确认"已经抓到的正文。
- 一次搜索 + 两三次抓取通常足够回答一个有争议的事实问题；超过这个量级先检查查询是否写得太散。
- 用户明确要求"多找几个来源"时再扩大范围，并在回复里列出实际来源数量和类型。
- 并发降低的是等待时间，不是积分：3 个并行查询仍是 3 次计费。用并发换广度，用浏览器换深度。
